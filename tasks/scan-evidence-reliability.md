# 掃描可信度開發計畫

優先修正掃描者能在結果頁看見、且可以用原始觀測重現的錯誤。每票從最新 main 開分支，先寫出能重現故障的失敗測試，再實作、獨立審查及修正。PR 與分支 CI 通過後合併，確認 merge SHA 的 main CI，才進下一票。

## S1　本票：斷路器和部分掃描的判讀

- 用受控 HTTP adapter 開啟斷路器，記錄實際請求數，覆蓋 status、headers、http-security。被攔截時保留抓取失敗。實際收到的 HTTP 回應仍須交給原模組判讀。
- 使用已保存的 status 和 headers 重播部分掃描。HSTS 的啟用與 preload 相容程度分開判斷；缺少 SSL、DNSSEC 或 WAF 觀測時，不產生該項發現。保留真的缺少標頭和顯式負值。
- 讓詳情、發現投影、比較及新產生的報告使用一致的觀測來源。附錄分清跳過、失敗及已量測的耗時。歷史下載維持原始位元組。需要重算舊投影時走既有的版本對帳流程。
- 驗收包含原始失敗案例、真實 HTTP 回應對照、手動重試與批次的資料格式、前端未知值、報告輸出及 CI。既有綜合分數的權重和歷史分數不在本票重校。

本機重播同一筆 TurnCheckHK 掃描時，34 個模組中只有 status 和 headers 取得結果。修正前列出 6 項發現，並顯示 HSTS 未啟用、SSL C 級、DNSSEC 未啟用。修正後保留實際缺少的 Permissions-Policy，HSTS 為已啟用，SSL 與 DNSSEC 為未知。這次比對重用原始量測。

## S2　區分「有 HTTP 回應」及「成功取得可分析內容」

- 從 status 的目標回應與 module 失敗信封開始。為實際 403、429、503、DNS 錯誤、TLS 錯誤、逾時及斷路器開啟建立可控的本機案例。
- 將目標回應碼、連線結果與模組錯誤分開保存；結果頁應能說明「HTTP 403，拒絕存取」。檢查登入頁、WAF 挑戰頁或轉址後內容會否被當作原站內容。回應類別清楚後，再根據重現證據決定哪些 GET/HEAD 適合有限次重試。
- 驗收要求無回應時不產生目標狀態碼，實際回應碼不會因任務狀態消失，阻擋頁不會觸發原站內容缺失的整改建議。記錄每個案例的實際請求數。

## S3　用標註案例決定下一輪修哪個探針

- 先重播固定語料，按模組記錄已知陽性、已知陰性、未知、抓取失敗及誤判；回歸測試不依賴外站。優先覆蓋 DNS 別名與 DNSSEC 紀錄型別、憑證證據不全、反向代理及標頭值解析。
- 以人工核對的案例為分母分開報告誤報與漏報，並列出無法判讀的比例。依重現頻率、影響的使用者決策和修正成本選下一票。單一網站的部分掃描無法估算整體誤報率。
- 在有涵蓋率對照的案例後，再評估部分掃描的數值評分與呈現，包括零個有效檢查的分類及未執行威脅模組對總分的影響。

## 週報維運的獨立驗證

沿用已授權的一個週期與本機收件匣。每半小時唯讀查排程及 run，核對到期時間、派工、終態和收件數。手動送出及故障演練各自驗證另一條路徑。七天後停用測試排程，依實際結果決定 W3 或維運觀測票。掃描開發不必等週期結束。
